# symphony-cli guide

Generated by `symphony-cli generate-guide`. It describes the binary it lies
next to; generate it again after an upgrade. The same facts as JSON:
`symphony-cli --json-help`. One command explained: `symphony-cli <command> --help`.

Symphony runs a topology of microservice building blocks as real Docker
containers, drives load through it, injects faults and runs predefined test
scenarios, to compare how **orchestration** and **choreography** behave under
stress. `symphony-cli` is the whole of it from a terminal: the same engine,
the same state and the same containers as the desktop app, which shows what
the CLI changes within a few seconds.

## Concepts

| word | meaning |
|------|---------|
| template | a topology that can be applied: one of the built-in ones, one you saved, or a JSON file |
| deployment | a template that is applied: one Docker network, one container per node replica. It is known by the name it was applied under (the template's name unless `--name` was given) |
| node | one building block: `infra` (the gateway: ingress and load generator), `service`, `broker`, `db`, `proxy` |
| edge | a link between two nodes: `calls`, `uses`, `publishes`, `subscribes`. Edge ids are what link faults take |
| saga | one request through the topology, from the gateway to its outcome (ok, failed, compensated, timeout) |
| hot config | keys of a node that change live, without a restart (`config`) |
| cold config | keys that are part of the container: changing one recreates the node (`apply`) |
| run | one stored execution of a test scenario against a template |

Where an argument says `<template>` it takes a template name, the name of a
running deployment, or a path to a topology JSON file (`-` reads stdin).
Where it says `<deployment>` it takes the name something was applied under.
Names with spaces need quotes: `"Orchestration (saga)"`.

## Conventions

Global flags go **before** the command:

| flag | effect |
|------|--------|
| `--db FILE` | state database (default: symphony.db next to the binary, or $SYMPHONY_DB) |
| `--json` | print the result as JSON instead of text |
| `-v` | print every engine log line, not only warnings and errors |
| `--help` | this help; after a command, that command's help |
| `--json-help` | everything here, and the fault kinds, scenarios and templates, as one JSON document (for scripts and agentic models) |

Exit codes:

| code | meaning |
|------|---------|
| 0 | the command did what it was asked |
| 1 | it failed (the reason is on stderr) |
| 2 | it was called wrongly (the usage is on stderr) |
| 3 | a test ran to its end and did not pass |

- Results and the progress of an apply go to stdout; warnings and errors go
  to stderr.
- `key=value` arguments: the value is read as JSON when it parses (`rps=40`,
  `peers='["payment"]'`), else as a string.
- State lives in `symphony.db` next to the binary (`--db FILE` or
  `$SYMPHONY_DB` moves it). The window and the CLI share it. Containers keep
  running after a command returns.
- Docker must be running for everything that touches containers. Templates,
  validation, scenarios and stored runs work without it.
- The first `apply` on a machine builds the five block images, which takes a
  minute or two.

## For agentic models

Read this section and [Workflows](#workflows) before running anything; fetch
`symphony-cli --json-help` when you need the exact arguments of a command.

1. **Discover, do not guess.** `symphony-cli templates` lists what can be
   applied, `status` what is applied, `inspect <deployment>` the node and edge
   ids, `scenarios` the tests, `--json-help` everything else. Ids differ
   between templates.
2. **Pass `--json`** (before the command) wherever you parse the answer:
   `status`, `inspect`, `templates`, `plan`, `validate`, `scenarios`, `runs`,
   `run`, `compare`, `test`, `top`, `logs`, `log`, `ps`, `load`. `show` and
   `control` always answer in JSON. `apply`, `teardown`, `fault`, `clear`, `config` and
   `resources` print one line of text and say whether they worked through the
   exit code.
3. **Check the exit code** of every command (table above). Code 3 from `test`
   is a result, not an error: the run finished and did not pass.
4. **Know which commands do not return at once:**
   - `apply`: until every node is healthy (the first apply builds the block images, which takes a minute or two)
   - `fault`: with --for, for kill, pause, crash and a whole-node partition: until the fault ends (Ctrl-C ends it early)
   - `top`: until Ctrl-C, unless --count is given
   - `log`: until Ctrl-C, unless --for is given
   - `test`: until the run ends (a scenario's duration_s, a minute by default); Ctrl-C aborts it
   Use `top --count N` and `log --for 10s` rather than the endless forms.
5. **A fault without `--for` stays until it is cleared.** Prefer `--for`. When
   you are done with a node, `clear <deployment> <node>` ends every fault on
   it. `status` and `inspect` show what state the nodes are in.
6. **Clean up what you created**: `teardown <deployment>` removes its
   containers and network. Do not tear down deployments you did not apply
   unless you were asked to.
7. **Keep experiments apart** with `--name` on `apply` and `test`: the same
   template can run several times under different names. To leave the user's
   state untouched altogether, work on a database of your own with
   `--db /path/to/scratch.db`.
8. **Comparing the two styles** means running the same scenario with the same
   parameters on both templates and then `compare <run> <run>`.

## Workflows

### Start a system and look at it

```sh
symphony-cli templates
symphony-cli apply "Orchestration (saga)"
symphony-cli status
symphony-cli inspect "Orchestration (saga)"            # nodes, edges and their ids
symphony-cli inspect "Orchestration (saga)" payment    # one node: health checks, config, limits
```

### Drive load and watch

```sh
symphony-cli load "Orchestration (saga)" rps=40 concurrency=32
symphony-cli top "Orchestration (saga)" --count 10     # one line a second
symphony-cli control "Orchestration (saga)" gateway sagas.summary
symphony-cli load "Orchestration (saga)" stop
```

### Break something by hand

```sh
# a link: drop 30% of the calls to payment for 20 seconds
symphony-cli fault "Orchestration (saga)" e-proxy-pay drop rate=0.3 --for 20s
# a node: freeze inventory for 10 seconds (the command stays until it ends)
symphony-cli fault "Orchestration (saga)" inventory pause --for 10s
# until further notice, then undo it
symphony-cli fault "Orchestration (saga)" payment latency ms=250 jitter_ms=50
symphony-cli clear "Orchestration (saga)" payment
```

### Compare orchestration with choreography

```sh
symphony-cli scenarios
symphony-cli test t04-crash "Orchestration (saga)"     # exits 3 if it does not pass
symphony-cli test t04-crash "Choreography (saga)"
symphony-cli runs                                      # the two run ids
symphony-cli compare <run id> <run id>
symphony-cli --json run <run id>                       # with the series
```

A scenario applies the template if it is not running, starts from a clean
state, and puts the template back as it was when it ends.

### Tune a running node

```sh
symphony-cli config "Orchestration (saga)" orchestrator timeout_ms=1500 retry_max=1
symphony-cli resources "Orchestration (saga)" payment --cpus 0.25 --memory-mb 128
symphony-cli logs "Orchestration (saga)" payment -n 50
```

### Build a system of your own

```sh
symphony-cli show "Orchestration (saga)" > my-system.json   # a file to start from
# edit my-system.json: nodes, edges, replicas, config
symphony-cli validate my-system.json
symphony-cli plan my-system.json                             # what apply would do
symphony-cli apply my-system.json
symphony-cli save my-system.json --name "My system"          # keep it as a template
```

Applying a changed file to a running deployment changes it in place; `plan`
says which nodes would be recreated.

### Clean up, or pick up where things were left

```sh
symphony-cli teardown "Orchestration (saga)"
symphony-cli restore        # after a reboot or a Docker restart: recreate what is stored
```

## Commands

### Topologies

#### templates

`symphony-cli templates`

List the built-in and the saved templates.

```sh
symphony-cli templates
```

Docker: no. Only reads.

#### show

`symphony-cli show <template|file>`

Print a template as JSON.

Edit the output and give the file to apply, plan or save.

```sh
symphony-cli show "Orchestration (saga)" > my-system.json
```

Docker: no. Only reads.

#### save

`symphony-cli save <file|-> [--name NAME]`

Save a topology JSON file (- reads stdin) as a template.

A template of the same name is replaced.

- `--name NAME`: save it under this name instead of the one in the file

```sh
symphony-cli save my-system.json --name "My system"
```

Docker: no. Changes state.

#### delete

`symphony-cli delete <template>`

Delete a saved template.

```sh
symphony-cli delete "My system"
```

Docker: no. Changes state.

#### validate

`symphony-cli validate <template|file>`

Check a topology and list what is wrong with it.

Exits 1 when it has errors; warnings do not fail it.

```sh
symphony-cli validate my-system.json
```

Docker: no. Only reads.

#### plan

`symphony-cli plan <template|file> [--name NAME]`

List the operations apply would run, against what is running under that name.

Nothing is changed.

- `--name NAME`: plan it under this deployment name

```sh
symphony-cli plan my-system.json
```

Docker: optional. Only reads.

#### apply

`symphony-cli apply <template|file> [--name NAME]`

Apply a topology and wait until it runs.

A topology already running under that name is changed in place: hot config
live, cold config by recreating the node.

- `--name NAME`: apply it under this deployment name, next to others of the same template

```sh
symphony-cli apply "Orchestration (saga)"
symphony-cli apply my-system.json --name "Experiment 1"
```

Docker: required. Changes state. Does not return at once: until every node is healthy (the first apply builds the block images, which takes a minute or two).

#### teardown

`symphony-cli teardown <deployment>`

Remove a deployment's containers and network, and forget it.

```sh
symphony-cli teardown "Orchestration (saga)"
```

Docker: required. Changes state.

#### restore

`symphony-cli restore`

Recreate stored deployments whose containers are gone; end overdue faults.

A deployment is recreated when a container of it is gone or stopped (a reboot, a
Docker restart). The desktop app does this by itself when it starts.

```sh
symphony-cli restore
```

Docker: required. Changes state.

### Deployments

#### status

`symphony-cli status`

Docker, the state database and every deployment with its phase.

```sh
symphony-cli status
symphony-cli --json status
```

Docker: optional. Only reads.

#### inspect

`symphony-cli inspect <deployment> [node]`

A deployment's nodes and edges, or one node's health checks, config and limits.

The node and edge ids it prints are what config, resources, fault and logs take.

```sh
symphony-cli inspect "Orchestration (saga)"
symphony-cli inspect "Orchestration (saga)" payment
```

Docker: required. Only reads.

#### config

`symphony-cli config <deployment> <node> key=value...`

Change hot config keys of a running node, live.

Only keys the node's hot config already has can be set (inspect lists them).

```sh
symphony-cli config "Orchestration (saga)" orchestrator timeout_ms=1500 retry_max=1
```

Docker: required. Changes state.

#### resources

`symphony-cli resources <deployment> <node> [--cpus N] [--memory-mb N] [--pids N]`

Change a running node's CPU, memory and pid limits in place (0 = unlimited).

Without a flag it prints the limits.

- `--cpus N`: CPU limit in cores, e.g. 0.25
- `--memory-mb N`: memory limit in MB (a hard limit: beyond it the container is OOM-killed)
- `--pids N`: limit on the number of processes

```sh
symphony-cli resources "Orchestration (saga)" payment --cpus 0.25 --memory-mb 128
```

Docker: required. Changes state.

#### fault

`symphony-cli fault <deployment> <node|edge> <kind> [--for DURATION] [key=value...]`

Inject a fault into a node, or into the link an edge is.

kinds: kill, pause, partition, cpu_stress, memory_pressure, stall, crash, drop, error, latency, timeout, slow, corrupt, duplicate, reorder, reject
Without --for the fault stays until `clear`. kill, pause, crash and a whole-node
partition do not end by themselves, so with --for symphony-cli stays until they do.
key=value are the kind's knobs, e.g. ms=250 for latency, rate=0.2 for drop.

- `--for DURATION`: end the fault after this long, e.g. 10s or 1m30s (default: until cleared)

```sh
symphony-cli fault "Orchestration (saga)" e-proxy-pay drop rate=0.3 --for 20s
symphony-cli fault "Orchestration (saga)" inventory pause --for 10s
symphony-cli fault "Orchestration (saga)" payment latency ms=250 jitter_ms=50
```

Docker: required. Changes state. Does not return at once: with --for, for kill, pause, crash and a whole-node partition: until the fault ends (Ctrl-C ends it early).

#### clear

`symphony-cli clear <deployment> <node|edge>`

Clear every fault on a node, whoever injected it.

Given an edge, it clears the node that sends on it.

```sh
symphony-cli clear "Orchestration (saga)" payment
```

Docker: required. Changes state.

#### load

`symphony-cli load <deployment> [stop | key=value...] [--node GATEWAY]`

Drive load through the gateway, stop it, or (no arguments) show it.

keys: rps, pattern (constant|ramp|burst|sine|step), to_rps, factor, burst_ms,
period_ms, step_every_ms, step_rps, duration_ms (0 = until stopped), concurrency,
payload_bytes. A load without an end is restarted when the deployment is reopened.

- `--node GATEWAY`: the gateway to use when the topology has several

```sh
symphony-cli load "Orchestration (saga)" rps=40 concurrency=32
symphony-cli load "Orchestration (saga)" pattern=ramp rps=10 to_rps=200 duration_ms=60000
symphony-cli load "Orchestration (saga)"
symphony-cli load "Orchestration (saga)" stop
```

Docker: required. Changes state.

#### control

`symphony-cli control <deployment> <node> <op> [key=value...]`

Send a raw /control command to every replica of a node.

The first replica's answer is printed, as JSON. The op `ops` lists what a node understands; config.get, fault.list, sagas.summary,
sagas.recent, behaviour.get and topics.get only read.

```sh
symphony-cli control "Orchestration (saga)" gateway sagas.summary
symphony-cli control "Orchestration (saga)" payment ops
```

Docker: required. Changes state.

#### logs

`symphony-cli logs <deployment> <node> [-n LINES]`

A node's recent log lines.

- `-n LINES`: how many lines (default 100)

```sh
symphony-cli logs "Orchestration (saga)" orchestrator -n 50
```

Docker: required. Only reads.

#### top

`symphony-cli top [deployment] [--count N]`

Live run metrics, one line a second, for one deployment or all of them.

sagas/s, p50 and p99 latency, failure rate, consumer lag, CPU, active faults.

- `--count N`: print N lines and return (default: until Ctrl-C)

```sh
symphony-cli top "Orchestration (saga)"
symphony-cli --json top "Orchestration (saga)" --count 5
```

Docker: required. Only reads. Does not return at once: until Ctrl-C, unless --count is given.

#### ps

`symphony-cli ps [-a]`

Every container on the machine, like docker ps, with Symphony's own marked.

- `-a`: include the stopped ones

```sh
symphony-cli ps
```

Docker: required. Only reads.

#### log

`symphony-cli log [--for DURATION]`

Follow what every container of Symphony prints, and the engine's own log.

- `--for DURATION`: follow for this long and return, e.g. 10s (default: until Ctrl-C)

```sh
symphony-cli log
symphony-cli log --for 10s
```

Docker: required. Only reads. Does not return at once: until Ctrl-C, unless --for is given.

### Tests

#### scenarios

`symphony-cli scenarios`

The predefined test scenarios, with their parameters.

```sh
symphony-cli scenarios
```

Docker: no. Only reads.

#### test

`symphony-cli test <scenario> <template|file> [--name NAME] [param=value...]`

Run a scenario against a template and wait for the verdict.

The template is applied first when it is not running. Exits 3 when the run does
not pass. The deployment is returned to the template afterwards and keeps running.

- `--name NAME`: run it on the deployment of this name

```sh
symphony-cli test t04-crash "Choreography (saga)"
symphony-cli --json test t01-baseline "Orchestration (saga)" rps=80 duration_s=30
```

Docker: required. Changes state. Does not return at once: until the run ends (a scenario's duration_s, a minute by default); Ctrl-C aborts it.

#### runs

`symphony-cli runs`

Stored test runs, newest first.

```sh
symphony-cli runs
```

Docker: no. Only reads.

#### run

`symphony-cli run <id>`

One run's phases, summary and assertions (with --json: its series too).

```sh
symphony-cli run t04-crash-choreography-saga-1790000000
```

Docker: no. Only reads.

#### compare

`symphony-cli compare <id> <id>`

Two runs' summaries side by side.

```sh
symphony-cli compare <run on one template> <run on the other>
```

Docker: no. Only reads.

#### rm-run

`symphony-cli rm-run <id>`

Delete a stored run.

```sh
symphony-cli rm-run t04-crash-choreography-saga-1790000000
```

Docker: no. Changes state.

### Help

#### help

`symphony-cli help [command]`

This list, or one command explained.

`symphony-cli <command> --help` is the same as `symphony-cli help <command>`.

```sh
symphony-cli help

```

`symphony-cli generate-guide [--out FILE]`

with examples, and lists every command, fault kind and scenario. It is written for

- `--out FILE`: write it there instead (- prints it)

```sh
symphony-cli generate-guide
symphony-cli generate-guide --out -
```

Docker: no. Only reads.

## Fault kinds

`symphony-cli fault <deployment> <node|edge> <kind> [--for DURATION] [key=value...]`

Given a node, a fault hits the whole node. Given an edge, a link fault hits
that one link, on its sending side. Kinds marked *stays* do not end by
themselves: with `--for` the command waits and ends them, without it they
last until `clear`.

| kind | carried out by | parameters (defaults) | effect |
|------|----------------|-----------------------|--------|
| `kill` *stays* | Docker |  | SIGKILL the node's containers; they are started again when the fault ends |
| `pause` *stays* | Docker |  | freeze the node's processes |
| `partition` *stays* | Docker, or the block with peers | `peers=["node",...]` | cut the node off the network; with peers, refuse traffic to and from those nodes only |
| `cpu_stress` | the block | `cores=1` | burn CPU inside the container (10s unless --for says otherwise) |
| `memory_pressure` | the block | `mb=100` | allocate and hold memory inside the container |
| `stall` | the block |  | freeze the data path while the admin port keeps answering (5s unless --for says otherwise) |
| `crash` *stays* | the block | `exit_code=137` | the process exits; it is started again when the fault ends |
| `drop` | the block, per request | `rate=1` | swallow a share of the requests or messages |
| `error` | the block, per request | `rate=1 status=503` | answer a share of the requests with an error |
| `latency` | the block, per request | `ms=100 jitter_ms=0 rate=1` | delay requests |
| `timeout` | the block, per request | `rate=1` | hang until the caller gives up |
| `slow` | the block, per request | `bytes_per_sec=1024` | throttle the response body |
| `corrupt` | the block, per request | `rate=1` | answer with a malformed body |
| `duplicate` | the block, per request | `rate=1` | deliver a share of the requests twice |
| `reorder` | the broker |  | deliver messages out of order (on a subscribes edge) |
| `reject` | the block, per request | `rate=1` | refuse connections |

`rate` is the share of requests hit, from 0 to 1.

## Load generator

`symphony-cli load <deployment> key=value...` drives sagas through the gateway.

| key | meaning |
|-----|---------|
| `rps` | target sagas per second (required) |
| `pattern` | `constant` (default), `ramp`, `burst`, `sine`, `step` |
| `to_rps` | where a `ramp` ends, over `duration_ms` |
| `factor`, `burst_ms`, `period_ms` | `burst`: rps × factor for burst_ms every period_ms |
| `step_rps`, `step_every_ms` | `step`: add step_rps every step_every_ms |
| `duration_ms` | stop by itself after this long; 0 or absent: until `load <deployment> stop` |
| `concurrency` | sagas in flight at most (default 64); beyond it the generator sheds |
| `payload_bytes` | size of each request's payload |

## Scenarios

`symphony-cli test <scenario> <template> [param=value...]`

Every scenario is a timeline of load, faults, limits and config changes with
assertions per phase. The parameters shown are the defaults; any can be
overridden on the command line.

- **`t01-baseline`** Baseline: Constant load for the whole run; the reference numbers every other scenario is compared against. *Shows:* The cost of the broker hop versus the orchestrator's sequential calls at equal load.
  Parameters: `concurrency=64` `duration_s=60` `rps=50`
- **`t02-ramp`** Ramp to saturation: Load ramps from a few rps to max_rps; the knee where latency departs from linear and errors start is the capacity. *Shows:* The capacity of each style with equal resources, and which component saturates first.
  Parameters: `concurrency=128` `duration_s=90` `max_rps=400` `ramp_ms=90000` `rps=5`
- **`t03-burst`** Burst: Baseline rps with periodic bursts of factor x for burst_ms every period_ms. *Shows:* How queues (broker) absorb spikes versus how synchronous chains reject them.
  Parameters: `burst_ms=2000` `concurrency=128` `duration_s=60` `factor=5` `period_ms=10000` `rps=30`
- **`t04-crash`** Service crash mid-saga: Steady load; a participant service is killed for down_s and restarted. *Shows:* Orchestration compensates and fails fast; choreography queues and replays. Same outage, different failure shapes.
  Parameters: `concurrency=64` `down_s=10` `duration_s=60` `rps=40`
- **`t05-link-latency`** Link latency: +ms of latency on the proxied link for the fault phase. *Shows:* Latency amplification through timeouts and retries; whether the retry budget makes things worse.
  Parameters: `concurrency=64` `duration_s=60` `jitter_ms=50` `ms=300` `rps=40`
- **`t06-link-loss`** Link packet loss: Drop a share of the requests on the proxied link. *Shows:* At-least-once delivery hides loss but costs duplicates; synchronous calls surface loss as failures.
  Parameters: `concurrency=64` `duration_s=60` `rate=0.3` `rps=40`
- **`t07-partition`** Selective partition: Cut the proxied link entirely (100% drop) for the fault phase, then heal. *Shows:* The broker keeps the system alive at the cost of lag and memory; the orchestrator fails sagas immediately.
  Parameters: `concurrency=64` `duration_s=70` `rps=40`
- **`t08-central-outage`** Central component outage: Pause the component everything depends on (the broker, or the first service) for down_s. *Shows:* The single point of failure of each style and how it recovers.
  Parameters: `concurrency=64` `down_s=10` `duration_s=60` `rps=40`
- **`t09-pool-exhaustion`** Database pool exhaustion: Shrink the database's connection pool to a handful while at load, then restore it. *Shows:* How a small dependency limit propagates through each chain.
  Parameters: `concurrency=64` `duration_s=60` `max_connections=3` `rps=40`
- **`t10-cpu-throttle`** CPU throttling: Limit a participant to cpus cores through Docker during the pressure phase. *Shows:* External resource pressure versus internal behaviour; which style degrades gracefully.
  Parameters: `concurrency=64` `cpus=0.1` `duration_s=60` `rps=40`
- **`t11-oom`** Memory limit and OOM: Set a low memory limit on a participant, then make it allocate until the kernel kills it; it is restarted after restart_delay_s. *Shows:* A crash the process cannot handle; restart behaviour of each style.
  Parameters: `alloc_mb=256` `concurrency=64` `duration_s=60` `memory_mb=64` `restart_delay_s=5` `rps=30`
- **`t12-slow-consumer`** Slow consumer: Make one consumer/participant hold each request for io_ms. *Shows:* Backpressure by queueing (lag grows) versus backpressure by blocking (latency grows).
  Parameters: `concurrency=64` `duration_s=60` `io_ms=200` `rps=40`
- **`t13-retry-storm`** Retry storm: Halve the entry service's timeout, raise its retries, then add latency on the proxied link. *Shows:* Misconfigured resilience is worse than none: request amplification and what the circuit breaker prevents.
  Parameters: `concurrency=64` `duration_s=60` `ms=200` `retry_max=6` `rps=30` `timeout_ms=150`
- **`t14-hot-config`** Hot config under load: Change hot keys (timeout, retries) at steady load, then a cold key (workers) that recreates the container. *Shows:* The value of the hot/cold split: a blip for hot changes, downtime for cold ones.
  Parameters: `concurrency=64` `duration_s=60` `rps=40`
- **`t15-scale-out`** Scale out under load: Raise the participant's replicas 1 -> replicas (a cold recreate) at load, then back. *Shows:* How each style copes with topology change and whether client-side load balancing spreads the load.
  Parameters: `concurrency=64` `duration_s=70` `replicas=3` `rps=40`
- **`t16-duplicates`** Duplicate delivery: Duplicate a share of the messages/calls on the proxied link. *Shows:* Idempotency as a measurable requirement: duplicates deduplicated versus processed twice.
  Parameters: `concurrency=64` `duration_s=60` `rate=0.3` `rps=40`
- **`t17-chaos-soak`** Chaos soak: Steady load with a different fault every interval_s: latency, drop, kill, pause, pool shrink, cpu burn. *Shows:* The aggregate resilience score: availability, worst p99 and recovery after each kind of fault.
  Parameters: `concurrency=64` `duration_s=180` `interval_s=20` `rps=30`
- **`t18-cold-start`** Cold start: Tear the template down, apply it again, and measure until traffic flows. *Shows:* The cost of the broker/database warm-up and the order of readiness.
  Parameters: `concurrency=32` `duration_s=45` `rps=20`

## Built-in templates

### Orchestration (saga)

Nodes: gateway (infra), orchestrator (service), toxiproxy (proxy), payment (service), inventory (service), shipping (service), postgres (db)

Edges:

- `e-gw-orch: gateway -calls-> orchestrator`
- `e-orch-proxy: orchestrator -calls-> toxiproxy`
- `e-proxy-pay: toxiproxy -calls-> payment`
- `e-orch-inv: orchestrator -calls-> inventory`
- `e-orch-ship: orchestrator -calls-> shipping`
- `e-orch-db: orchestrator -uses-> postgres`

### Choreography (saga)

Nodes: gateway (infra), order (service), kafka (broker), toxiproxy (proxy), payment (service), inventory (service), postgres (db)

Edges:

- `e-gw-order: gateway -calls-> order`
- `e-order-pub: order -publishes-> kafka`
- `e-proxy-sub: kafka -subscribes-> toxiproxy`
- `e-pay-sub: toxiproxy -subscribes-> payment`
- `e-pay-pub: payment -publishes-> kafka`
- `e-inv-sub: kafka -subscribes-> inventory`
- `e-inv-pub: inventory -publishes-> kafka`
- `e-order-sub: kafka -subscribes-> order`
- `e-order-db: order -uses-> postgres`

## A topology file

`symphony-cli show <template>` prints one to start from. Its shape:

```json
{
  "version": 2,
  "name": "My system",
  "nodes": [
    {
      "id": "payment",
      "kind": "service",
      "image": "symphony/service:dev",
      "replicas": 2,
      "position": {"x": 760, "y": 100},
      "config": {"hot": {"timeout_ms": 800}, "cold": {"workers": 32}},
      "resources": {"cpus": 0.5, "memory_mb": 256}
    }
  ],
  "edges": [
    {"id": "e-orch-pay", "from": "orchestrator", "to": "payment", "kind": "calls"},
    {"id": "e-order-pub", "from": "order", "to": "kafka", "kind": "publishes", "topic": "order.created"}
  ]
}
```

- `kind` of a node: `infra` (gateway), `service`, `broker`, `db`, `proxy`.
  A topology needs a gateway to take load.
- `kind` of an edge: `calls` (service to service, or through a proxy), `uses`
  (to a db), `publishes` (to a broker, with a `topic`), `subscribes` (from a
  broker, with a `topic`).
- Ids may hold letters, digits, `-`, `_` and `.`.
- What a service does with a request follows from its edges: one that calls
  others is an orchestrator, one that only answers is a participant, one that
  subscribes and publishes is a choreography step.
- `symphony-cli validate` says what is wrong with a file before anything runs.
